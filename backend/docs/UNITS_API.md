# واحد کالا و قرارداد جدید Items

انتیتی `Unit` در جدول `Units` ذخیره می‌شود. واحدها مانند کالاها سراسری هستند
و به شعبه محدود نیستند. نام واحد الزامی و حداکثر ۱۶ کاراکتر است؛ توضیحات
اختیاری و حداکثر ۵۰۰ کاراکتر است. نام واحد فعال تکراری پذیرفته نمی‌شود.

| عملیات | API | مجوز |
|---|---|---|
| لیست و جستجو | `GET /api/units?search=کیلو&page=1&pageSize=50` | `Unit.Read` |
| دریافت تکی | `GET /api/units/1` | `Unit.Read` |
| ایجاد | `POST /api/units` | `Unit.Create` |
| ویرایش | `PUT /api/units/1` | `Unit.Update` |
| حذف نرم | `DELETE /api/units/1?rowVersion=BASE64_URL_ENCODED` | `Unit.Delete` |

بدنهٔ ایجاد:

```json
{ "name": "کیلوگرم", "description": "واحد وزن" }
```

بدنهٔ ویرایش:

```json
{ "id": 1, "name": "کیلوگرم", "description": "واحد وزن", "rowVersion": "توکن دریافتی از API" }
```

خروجی تکی شامل `id`, `name`, `description`, `rowVersion`, `createdAtUtc`,
`updatedAtUtc` است. لیست، ساختار صفحه‌بندی معمول پروژه را دارد.
ایجاد وضعیت ۲۰۱، ویرایش وضعیت ۲۰۰ و حذف وضعیت ۲۰۴ برمی‌گرداند.
برای ویرایش و حذف، توکن `rowVersion` آخرین پاسخ را بفرستید؛ نسخهٔ قدیمی
خطای ۴۰۹ می‌دهد. واحد متصل به هر کالا، حتی کالای حذف‌شده، قابل حذف نیست.

## تغییر قرارداد کالا

در `POST /api/items` و `PUT /api/items/{id}` به جای `unit` متنی، `unitId`
عدد مثبت و شناسهٔ یک واحد موجود و حذف‌نشده را ارسال کنید. سایر فیلدهای
کالا مانند قبل هستند. خروجی لیست، دریافت تکی، ایجاد و ویرایش کالا شامل
`unitId` و `unitName` است. فیلتر لیست کالا نیز `GET /api/items?unitId=1` است.
کلاینت باید قبل از ثبت کالا، واحدها را از API دریافت کند.

نام واحد در گزارش موجودی و خروجی انبار از رابطهٔ جدید خوانده می‌شود.
`InvoiceLines.Unit` عمداً متنی باقی می‌ماند: این نام، اطلاعات تاریخی
فاکتور است و با تغییر نام واحد تغییر نمی‌کند. تبدیل سفارش به فاکتور نیز
نام واحد جاری کالا را در ردیف فاکتور ثبت می‌کند.

## اسکریپت دیتابیس

فایل `NormalizeItemUnits.sql` برای SQL Server و دیتابیس موجود این پروژه است.
از دیتابیسِ دارای جدول‌های `Items`, `RolePermissions`, `__EFMigrationsHistory`
استفاده کنید. اسکریپت روی دیتابیس اجرا نشده است.

اسکریپت در تراکنش، جدول `Units` را می‌سازد؛ نام‌های متمایز واحدهای فعلی
را از همهٔ کالاها، شامل کالاهای حذف‌شده، منتقل می‌کند؛ `UnitId` را پر
می‌کند؛ سپس ستون قدیمی `Items.Unit` را حذف و کلید خارجی را برقرار می‌کند.
فاصله‌های ابتدا و انتهای نام حذف می‌شود و نام خالی به «عدد» نگاشت می‌شود.
نام‌های غیرخالی ترجمه یا عوض نمی‌شوند. اجرای موفق در تاریخچهٔ EF ثبت
می‌شود و اجرای دوبارهٔ اسکریپت، آن migration را مجدداً اعمال نمی‌کند.

مجوزهای `Unit.*` مطابق مجوزهای موجود `Item.*` به نقش‌ها افزوده می‌شوند.
برای دریافت ادعاهای جدید در توکن، کاربران مجدداً وارد شوند.

اسکریپت را روی دیتابیس مقصد با SSMS یا ابزار SQL Server اجرا کنید. اجرای
اسکریپت دستی و اجرای migration توسط EF دو راه جایگزین برای همین تغییرند؛
تاریخچهٔ ثبت‌شده مانع اجرای تکراری می‌شود. برنامه در شروع معمول، migrationهای
اجرانشده را اجرا می‌کند؛ پس قرارداد جدید کلاینت و بک‌اند را هماهنگ منتشر کنید.

## بررسی

Build موفق؛ هر ۱۰۷ تست مجموعهٔ موجود و جدید موفق شد. بررسی EF نیز تأیید
کرد که مدل و snapshot نهایی با migration هماهنگ‌اند. اجرای واقعی اسکریپت
روی SQL Server در این بررسی انجام نشده است.
