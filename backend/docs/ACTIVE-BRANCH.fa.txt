راهنمای شعبه فعال، مشتری مشترک و دسترسی چندشعبه‌ای
تاریخ: ۲ نوامبر ۲۰۲۶

رفتار نهایی
-----------
کالا، خدمات، واحد، دسته‌بندی، پکیج، مشتری و تأمین‌کننده بین شعب مشترک‌اند.
انبار، حساب صندوق/بانک، سفارش، فاکتور، پرداخت، چک، موجودی، گردش انبار و مانده‌های
اول دوره شعبه‌ای باقی می‌مانند. عمومی بودن مشتری به معنی عمومی بودن حساب و مانده او نیست.
شناسه شعبه روی مشتری‌های قبلی برای حفظ سابقه نگه داشته شده است؛ برای محدودکردن
مشتری یا اعتبارسنجی سفارش/فاکتور/چک استفاده نمی‌شود. مشتری‌ها ادغام یا حذف نشده‌اند.

تنظیم کاربر
-----------
در مدیریت کاربران دو فیلد وجود دارد:
۱. شعبه پیش‌فرض: یک شعبه، برای پیشنهاد در شروع کار.
۲. شعب مجاز: انتخاب چند شعبه. شعبه پیش‌فرض همیشه به این مجموعه اضافه می‌شود.
مجوزهای نقش‌ها تعیین می‌کنند کاربر چه عملیاتی انجام بدهد؛ شعب مجاز تعیین می‌کنند کجا.
داشتن دسترسی به چند شعبه به تنهایی مجوز ایجاد/ویرایش/حذف عملیات نمی‌دهد.

پس از ورود، صفحه «انتخاب شعبه کاری» نشان داده می‌شود. کاربر شعبه را تأیید می‌کند
و سپس شروع به کار می‌کند. بالای برنامه نام شعبه فعال و گزینه تغییر شعبه دیده می‌شود.
انتخاب شعبه برای هر تب مرورگر جدا نگهداری می‌شود؛ پس از خروج پاک می‌شود.
تغییر شعبه صفحه را دوباره بارگذاری می‌کند تا داده‌ها و فرم‌های شعبه قبلی باقی نمانند.
قبل از تغییر شعبه، فرم‌های نیمه‌کاره ذخیره یا بسته شوند.
اگر کاربر شعبه‌ای ندارد، مدیر باید شعبه پیش‌فرض/مجاز را تعیین کند.

لیست‌ها و گزارش‌ها
-----------------
پیش‌فرض، فقط اطلاعات شعبه فعال نمایش داده می‌شود؛ حتی برای مدیر و شعبه مرکزی.
کنترل شعبه در API و لایه دیتابیس هم انجام می‌شود؛ صرفاً فیلتر نمایشی نیست.
تغییر دستی شناسه شعبه به شعبه‌ای خارج از دسترسی، خطای عدم دسترسی می‌دهد.
فیلتر یک شعبه مشخص باید به یکی از شعب مجاز اشاره کند.
مجوز جدید Branch.ViewAll امکان انتخاب هر شعبه فعال و نمایش صریح «همه شعب» را می‌دهد.
این مجوز در فرم نقش‌ها با عنوان «مشاهده و فیلتر همه شعب» آمده است و به نقش‌های
موجود خودکار اضافه نمی‌شود. برای اعطای آن به مدیر موردنظر، نقش را ویرایش کنید.
نمایش همه شعب فقط روی درخواست‌های خواندن فهرست‌ها و گزارش‌هاست؛ ثبت و تغییر عملیات
همیشه مربوط به شعبه فعال است. برای ویرایش سند شعبه دیگر، ابتدا شعبه فعال را تغییر دهید.
تنظیمات عمومی مدیریت و پاک‌سازی اطلاعات، تنظیمات سراسری سامانه‌اند؛ ابزار پاک‌سازی
همچنان با هشدار حذف همه اطلاعات عملیاتی و مجوزهای مستقل خودش کار می‌کند.

مانده مشتری و حساب‌ها
--------------------
یک مشتری مشترک می‌تواند در هر شعبه مانده اول دوره جدا داشته باشد.
شاخص یکتای قبلی ContactId به BranchId+ContactId تغییر کرده است.
مانده و صورت‌حساب عادی از عملیات شعبه فعال محاسبه می‌شوند؛ حالت همه شعب نیازمند
مجوز و انتخاب صریح است. انبار و حساب بانکی در فرم ثبت از شعبه فعال گرفته می‌شوند.
سوابق نظارتی جدید شناسه شعبه دارند؛ سوابق قدیمی که شعبه‌شان مشخص نیست حذف نشده‌اند،
ولی در حالت یک شعبه نمایش داده نمی‌شوند و با حالت مجاز همه شعب قابل مشاهده‌اند.

حذف نقش
-------
نقشی که فقط به کاربران حذف‌شده وصل است قابل حذف است؛ ارتباط‌های تاریخی حفظ می‌شوند.
اگر به کاربر حذف‌نشده‌ای وصل باشد، حتی اگر کاربر غیرفعال باشد، حذف مسدود می‌شود.
حذف نقش نرم است و سوابق حسابرسی/ارتباط‌های قدیمی از بین نمی‌روند.
شروع مجدد برنامه نقش حذف‌شده را خودکار دوباره نمی‌سازد.

ارتقای دیتابیس و انتشار
----------------------
migration جدید: 20261102034520_ActiveBranchWorkspace
SQL آماده: docs/active-branch-upgrade.sql
ساختارهای جدید: UserBranches و ستون nullable BranchId در AuditTrails؛
همچنین شاخص مانده اول دوره مشتری شعبه‌ای شده است. داده عملیاتی حذف نمی‌شود.
این کار روی دیتابیس واقعی اجرا نشده است. تست‌ها از دیتابیس‌های آزمایشی استفاده کرده‌اند.

برای ارتقا:
۱. از دیتابیس و تنظیمات خصوصی بکاپ بگیرید.
۲. اجرای قدیمی API/دیباگر و سرویس قدیمی متصل به همین دیتابیس را در بازه انتشار متوقف کنید.
۳. API و Angular را از همین نسخه دوباره Build/Publish کنید.
۴. SQL آماده فقط ارتقای این migration را پوشش می‌دهد و دیتابیس باید migration
   20261020000000_UserSessionTimeouts را از قبل داشته باشد. در SSMS دیتابیس درست را
   انتخاب و SQL را بازبینی و اجرا کنید. یا اجازه دهید شروع API جدید طبق رفتار موجود
   MigrateAsync را با تنظیمات واقعی Production اعمال کند؛ اجرای دستی SQL و شروع API
   migration را دوباره اعمال نمی‌کند چون تاریخچه migration ثبت می‌شود.
۵. خروج و ورود مجدد؛ شعبه پیش‌فرض/شعب مجاز کاربران را در مدیریت تنظیم کنید.
۶. فقط به نقش‌های مسئول گزارش چندشعبه‌ای Branch.ViewAll بدهید؛ بعد خروج و ورود مجدد.
۷. فاکتور/پرداخت/مانده مشتری در دو شعبه و خروجی گزارش‌ها را کنترل کنید.

کاربران موجود بدون رکورد UserBranches همچنان شعبه پیش‌فرض قبلی خود را دارند.
برای گسترش دسترسی، شعب جدید را در فرم کاربر انتخاب کنید. هیچ دسترسی همه‌شعبه‌ای
به خاطر نام مدیر یا شعبه مرکزی به صورت ضمنی اعطا نمی‌شود.
ابزار EF design-time برای تولید schema از اتصال ساختگی و بدون اطلاعات خصوصی استفاده می‌کند؛
برای اعمال ارتقا از SQL بازبینی‌شده یا شروع API با تنظیمات واقعی مقصد استفاده کنید.
برگشت migration پس از ثبت مانده‌های متعدد برای یک مشتری در شعب مختلف ممکن است با
شاخص یکتای نسخه قدیمی سازگار نباشد؛ برای برگشت نسخه، طرح بازیابی DB لازم است.

پشتیبانی و فرم طرف حساب
----------------------
شماره پشتیبانی: 09010259933؛ لینک تماس در صفحه ورود و پایین منوی اصلی اضافه شده است.
اطلاعات هویتی و تکمیلی طرف حساب داخل بخش اسکرول قرار دارند و ردیف ذخیره جداست.
بازکردن اطلاعات تکمیلی نباید دکمه ذخیره را از پنجره خارج کند؛ این حالت در پنجره

نکته محیط فعلی
-------------
نسخه Debug در Rider باز بود و فایل‌های DLL را قفل کرده بود. بررسی بک‌اند در خروجی
جدا با نام BranchWork انجام شد؛ برای دیدن تغییرات در اجرای عادی، IDE را Stop، سپس
Build و Run کنید. پروفایل https توسعه روی پورت 7001 است؛ 7000 سرویس قدیمی است.
