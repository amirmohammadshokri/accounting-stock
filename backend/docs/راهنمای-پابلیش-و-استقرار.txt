راهنمای فارسی پابلیش و استقرار حسابداری و انبار
تاریخ تهیه: ۲۰ اکتبر ۲۰۲۶

این راهنما برای نسخه فعلی پروژه، اجرای ویندوزی بدون IIS، و بسته سرویس ویندوز
تهیه شده است. فرمان‌های ساخت روی سیستم برنامه‌نویسی اجرا می‌شوند؛ تغییر تنظیمات
نصب‌شده و مدیریت سرویس‌ها روی سیستم مقصد انجام می‌شوند.
نام پوشه‌ها و شماره نسخه خروجی را برای هر انتشار متناسب با نسخه خود انتخاب کنید.
رمز واقعی SQL یا کلید خصوصی در این راهنما نوشته نشده است.

۱. ساختار فعلی اجرا
==================
مرورگر روی همان کامپیوتر مقصد:
  فرانت‌اند: https://localhost:4200
  بک‌اند: https://localhost:7000/api
  SQL فعلی: 192.168.100.92
  دیتابیس فعلی: AccountingDb

localhost همیشه به همان کامپیوتری اشاره می‌کند که درخواست را ارسال می‌کند.
برای همین، بسته فعلی برای اجرای فرانت‌اند و بک‌اند روی یک کامپیوتر مقصد است.
باز کردن برنامه از مرورگر کامپیوترهای دیگر، تنظیم آدرس API، CORS، گواهی و شبکه
را نیز لازم دارد؛ صرفاً باز کردن پورت فایروال کافی نیست.

پوشه نصب‌شده سرویس‌ها:
  C:\ProgramData\AccountingStockService

نام داخلی سرویس‌ها:
  AccountingStockBackend
  AccountingStockFrontend

۲. آماده‌سازی سیستم برنامه‌نویسی
===============================
برای ساخت خروجی بک‌اند، .NET SDK سازگار با پروژه لازم است؛ Runtime به‌تنهایی
فرمان‌های ساخت را تأمین نمی‌کند. پروژه API فعلی net8.0-windows است و در ساخت
قبلی از SDK نصب‌شده .NET 10 استفاده شد.
برای ساخت فرانت‌اند، Node.js و npm سازگار با Angular 20 لازم‌اند.
نسخه‌های نصب‌شده در محیط ساخت قبلی: Node 24.18.0 و .NET SDK 10.0.303.
این‌ها شرح محیط ساخت قبلی هستند، نه الزام به استفاده همیشگی از همین نسخه‌های دقیق.

بررسی ابزارها در PowerShell:
  dotnet --list-sdks
  node --version
  npm.cmd --version

قبل از ساخت، تغییرات را بررسی و نسخه را در Git ثبت کنید. نام یا Tag نسخه منتشرشده
را نگه دارید تا معلوم باشد هر سیستم دقیقاً کدام نسخه را اجرا می‌کند.

۳. پابلیش دستی بک‌اند
====================
روی سیستم برنامه‌نویسی، PowerShell را باز کنید:

  cd "C:\Users\s.asadi\Downloads\accounting-stock\backend"

فرمان زیر را یک‌خطی اجرا کنید:

  dotnet publish .\Accounting.Api\Accounting.Api.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=false -o .\output\release-v2\backend

توضیح گزینه‌ها:
  Release: ساخت نسخه مناسب انتشار.
  win-x64: ویندوز ۶۴ بیتی.
  self-contained true: همراه کردن Runtimeهای لازم در خروجی.
  PublishSingleFile=false: خروجی به شکل پوشه فایل‌ها باقی می‌ماند.
  -o: مسیر خروجی.

برای هر نسخه، پوشه خروجی تازه انتخاب کنید تا فایل‌های قدیمی با نسخه جدید مخلوط نشوند.
همه پوشه خروجی لازم است؛ فقط Accounting.Api.exe را منتقل نکنید.
در خروجی مستقل، روی مقصد SDK یا نصب جداگانه .NET لازم نیست.

اگر خطای NU1301 برای مسیر محلی ناموجود NuGet دریافت کردید، فرمان زیر منبع رسمی
را فقط برای همین ساخت استفاده می‌کند:

  dotnet publish .\Accounting.Api\Accounting.Api.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=false --source https://api.nuget.org/v3/index.json -o .\output\release-v2\backend

اگر ساخت خطا داشت، خروجی ناقص را منتشر نکنید. هشدارها را نیز بررسی کنید؛ صرف
موفق بودن ساخت، درست بودن اتصال SQL و رفتار برنامه را ثابت نمی‌کند.

۴. ساخت دستی فرانت‌اند
======================
روی سیستم برنامه‌نویسی:

  cd "C:\Users\s.asadi\Downloads\accounting-stock\frontend"
  npm.cmd ci
  npm.cmd run build -- --configuration production

npm ci بسته‌ها را مطابق package-lock.json نصب می‌کند. وقتی بسته‌ها از قبل نصب
هستند و وابستگی‌ها تغییر نکرده‌اند، برای هر Build لازم نیست آن را دوباره اجرا کنید.

خروجی:
  C:\Users\s.asadi\Downloads\accounting-stock\frontend\dist\accounting-web\browser

محتویات داخل browser را در پوشه frontend بسته انتشار قرار دهید؛ پوشه browser
را یک سطح اضافه داخل frontend کپی نکنید. index.html باید مستقیماً داخل frontend باشد.

آدرس API در ساخت production فعلی از این فایل می‌آید:
  frontend\src\environments\environment.ts

مقدار فعلی:
  apiBaseUrl: 'https://localhost:7000/api'

ساخت docker از environment.docker.ts استفاده می‌کند و API در آن /api است.
برای بسته سرویس ویندوز فعلی از configuration production استفاده کنید.
فایل‌های فرانت‌اند را با دوبارکلیک روی index.html اجرا نکنید؛ وب‌سرور لازم دارند.

۵. آماده‌سازی بسته انتقال و نصب تازه
===================================
dotnet publish فقط خروجی برنامه را می‌سازد؛ نصب‌کننده سرویس ایجاد نمی‌کند.
از ZIP خام بسته سرویس به‌عنوان قالب نگه‌داری کنید و برای هر نسخه از آن کپی بگیرید:
  backend\output\windows-service-20261020.zip

قالب شامل backend، frontend، runtime، services، فایل serve-frontend.cjs،
راه‌انداز HTTPS و اسکریپت‌های نصب و مدیریت است. آن را در Git نگه ندارید؛ حاوی
تنظیم خصوصی اتصال SQL است. خروجی‌های فعلی در backend\output قرار دارند و ignore شده‌اند.

برای نسخه جدید، خروجی جدید backend و محتوای browser جدید را در کپی قالب قرار دهید.
تنظیمات مقصد باید جدا مدیریت شوند. فایل appsettings.Production.json قالب را با
تنظیم توسعه به‌صورت ناخواسته جایگزین نکنید. Runtime همراه Node و فایل‌های WinSW
و مجوزهایشان را نیز نگه دارید.
برای سیستم مقصد جدید، گواهی و کلید ورود باید روی همان مقصد ایجاد شوند؛ پوشه‌ای
که روی یک سیستم دیگر Setup شده، قالب مناسب نصب عمومی نیست.

روی مقصد، ZIP را کامل استخراج کنید. سپس:
  ۱) اجرای دستی قبلی را متوقف و پورت‌های 7000 و 4200 را آزاد کنید.
  ۲) روی 1-Install-Services.cmd راست‌کلیک و Run as administrator را انتخاب کنید.
  ۳) اگر بسته قدیمی روی همین سیستم Setup شده است، مسیر پوشه والد backend و
     frontend را در Old package folder وارد کنید. تنظیمات، گواهی و App_Data حفظ می‌شوند.
  ۴) اگر پوشه قبلی وجود ندارد، Enter خالی بزنید تا تنظیم تازه انجام شود.
  ۵) پس از پایان نصب، پنجره را ببندید و https://localhost:4200 را باز کنید.

سرویس‌ها با Automatic Delayed Start، حساب محدود LocalService و بازیابی پس از
خطا تنظیم شده‌اند. برای کار عادی، CMD باز نمی‌ماند و ورود کاربر به ویندوز لازم نیست.
برقراری شبکه یا VPN به SQL همچنان لازم است. گواهی تازه دو سال اعتبار دارد؛ اگر
گواهی قدیمی حفظ شود، همان تاریخ انقضای قبلی برقرار است.

۶. به‌روزرسانی سیستمی که سرویس روی آن نصب است
===========================================
برای تغییر عادی فایل‌های برنامه، حذف و نصب مجدد سرویس لازم نیست.
پیش از انتقال نسخه جدید از SQL و پوشه نصب‌شده بکاپ بگیرید.

ترتیب کار روی مقصد:
  ۱) 4-Stop-Services.cmd را با Run as administrator اجرا کنید.
  ۲) فایل‌های جدید backend را در پوشه backend نصب‌شده جایگزین کنید.
  ۳) فایل‌های ساخته‌شده فرانت‌اند را در frontend نصب‌شده جایگزین کنید.
  ۴) 3-Restart-Services.cmd را با دسترسی مدیر اجرا کنید.
  ۵) ورود، ثبت اطلاعات، ویرایش، چاپ و مسیرهای فرانت‌اند را بررسی کنید.

این موارد نصب‌شده را حفظ کنید و با خروجی توسعه بازنویسی نکنید:
  backend\appsettings.Production.json
  backend\certificates
  backend\App_Data
  backend\Reporting\stimulsoft-license.private.json

اگر نام برنامه، مسیر فایل اجرایی یا تعریف سرویس‌ها عوض شود، مدیریت سرویس‌ها هم
باید متناسب با آن تغییر کند. پوشه نصب‌شده را جابه‌جا نکنید.
نصب‌کننده فعلی برای جلوگیری از حذف تنظیمات، روی پوشه نصب‌شده موجود نصب مجدد نمی‌کند.

رفتار مهم کد فعلی: هنگام شروع برنامه migrationها و داده‌های پایه اجرا می‌شوند.
نسخه جدید می‌تواند ساختار دیتابیس را به‌روز کند. بازگرداندن فایل‌های نسخه قبلی،
لزوماً migration را برنمی‌گرداند. برای بازگشت، وضعیت بکاپ دیتابیس را نیز در نظر بگیرید.

۷. تغییر آدرس SQL بدون پابلیش مجدد
=================================
روی مقصد با دسترسی مدیر این فایل را ویرایش کنید:
  C:\ProgramData\AccountingStockService\backend\appsettings.Production.json

قسمت ConnectionStrings و سپس Default را تغییر دهید. نمونه با مقادیر فرضی:

  "ConnectionStrings": {
    "Default": "Server=tcp:192.168.1.50,1433;Database=AccountingDb;User ID=accounting_user;Password=YOUR_PASSWORD;Encrypt=True;TrustServerCertificate=True;MultipleActiveResultSets=True"
  }

قسمت‌های رشته اتصال:
  Server: آدرس کامپیوتر SQL و پورت آن.
  Database: نام دیتابیس، نه نام پوشه ویندوز.
  User ID و Password: حساب ورود SQL.
  Encrypt=True: درخواست ارتباط رمزگذاری‌شده.
  TrustServerCertificate=True: پذیرفتن گواهی سرور بدون بررسی زنجیره اعتماد آن؛
    برای محیطی با گواهی معتبر SQL بهتر است اعتبارسنجی گواهی نیز فعال باشد.

آدرس SQL و پورت با ویرگول جدا می‌شوند:
  Server=192.168.1.50,1433
  Server=192.168.1.50,1500

برای Instance نام‌گذاری‌شده، در JSON بک‌اسلش دوبار نوشته می‌شود:
  "Default": "Server=SERVER-PC\\SQLEXPRESS;Database=AccountingDb;..."

در مثال آخر، ... فقط مخفف ادامه تنظیمات است؛ آن را در رشته اتصال واقعی نگذارید.
اگر رمز شامل کوتیشن یا بک‌اسلش است، قواعد JSON و رشته اتصال هر دو باید رعایت شوند؛
فایل تنظیمات باید JSON معتبر بماند. دیگر بخش‌ها مانند JwtSettings و Certificate را حذف نکنید.

بعد از ذخیره، سرویس‌ها را Restart کنید. برای تغییر SQL نیازی به Build یا Publish
فرانت‌اند و بک‌اند نیست. محیط فعال سرویس Production است؛ ویرایش فایل Development
به‌تنهایی تنظیم فعال این نصب را تغییر نمی‌دهد.
متغیرهای محیطی هم می‌توانند تنظیمات را override کنند؛ در بسته فعلی مقدار SQL در
XML سرویس نوشته نشده است و از فایل Production خوانده می‌شود.

تست دسترسی شبکه از کامپیوتر برنامه، با آدرس و پورت واقعی:
  Test-NetConnection 192.168.1.50 -Port 1433

TcpTestSucceeded=True فقط باز بودن مسیر TCP را نشان می‌دهد؛ نام دیتابیس و حساب
را جداگانه با SSMS یا اتصال برنامه بررسی کنید. روی SQL مقصد باید TCP/IP، سرویس SQL،
مجوز حساب و پورت مناسب فایروال آماده باشند. 1433 پورت رایج است، اما پورت واقعی
سرور تعیین‌کننده است. دسترسی دیتابیس را به شبکه لازم محدود کنید.

سرویس فعلی با LocalService اجرا می‌شود. اگر از SQL Authentication به اتصال
Integrated Security=True تغییر دهید، هویت حساب سرویس در احراز هویت SQL مؤثر است؛
این اتصال الزاماً با حساب کاربر واردشده به ویندوز انجام نمی‌شود.

انتقال دیتابیس با تغییر آدرس فرق دارد:
  اگر SQL به کامپیوتر جدید منتقل می‌شود، ابتدا بکاپ SQL را روی سرور جدید Restore
  کنید و حساب‌ها و مجوزها را آماده کنید؛ بعد رشته اتصال برنامه را تغییر دهید.
  مسیر فایل‌های MDF و LDF را روی خود SQL Server مدیریت می‌کنند. اتصال فعلی برنامه
  بر اساس Server و Database است و معمولاً مسیر فیزیکی این فایل‌ها در آن قرار نمی‌گیرد.

۸. تشخیص پورت اشغال‌شده
=======================
در PowerShell مدیر روی مقصد:

  Get-NetTCPConnection -LocalPort 7000 -State Listen | Select-Object LocalAddress,LocalPort,OwningProcess

عدد OwningProcess شناسه پردازش است. نمونه بررسی:
  Get-Process -Id 1234

برای فرانت‌اند:
  Get-NetTCPConnection -LocalPort 4200 -State Listen

اگر اجرای قدیمی همین برنامه پورت را گرفته، اجرای قبلی را متوقف کنید.
اگر سرویس همین برنامه از قبل روشن است، نسخه دستی دیگری را هم‌زمان اجرا نکنید.
پردازش ناشناس یا سرویس ویندوز را بدون شناخت متوقف نکنید؛ ممکن است برنامه دیگری
از آن استفاده کند. در این حالت پورت آزاد دیگری برای برنامه انتخاب کنید.

۹. تغییر پورت بک‌اند
====================
مثال: تغییر 7000 به 7443.

در appsettings.Production.json مقصد، فقط Url نقطه HTTPS را تغییر دهید:
  Kestrel > Endpoints > Https > Url
  https://localhost:7443

مسیر گواهی و Password فعلی را حفظ کنید. گواهی localhost به شماره پورت وابسته نیست.
سپس روی سیستم برنامه‌نویسی در frontend\src\environments\environment.ts:
  apiBaseUrl: 'https://localhost:7443/api'

فرانت‌اند را با configuration production دوباره Build کنید، خروجی را جایگزین و
سرویس‌ها را Restart کنید. برای تغییر صرف پورت API، Publish مجدد بک‌اند لازم نیست.
تغییر API در فایل environment روی سورس، فایل‌های فرانت‌اند قبلاً ساخته‌شده را
خودکار تغییر نمی‌دهد؛ Build جدید لازم است.

۱۰. تغییر پورت فرانت‌اند
========================
مثال: تغییر 4200 به 4300.

روی مقصد با دسترسی مدیر این فایل راه‌انداز را ویرایش کنید:
  C:\ProgramData\AccountingStockService\serve-frontend.cjs

شماره واقعی در server.listen را تغییر دهید:
  server.listen(4300, '127.0.0.1', ...)

این خط نمونه است؛ callback و بقیه کد خط موجود را حفظ کنید و فقط عدد پورت را
عوض کنید. آدرس نوشته‌شده در پیام console.log را هم برای جلوگیری از اشتباه اصلاح کنید.

در appsettings.Production.json مقصد، CORS را هماهنگ کنید:
  "Cors": {
    "AllowedOrigins": [
      "https://localhost:4300"
    ]
  }

سرویس‌ها را Restart و این آدرس را باز کنید:
  https://localhost:4300

برای تغییر فقط پورت سروکننده فرانت‌اند، Build مجدد Angular لازم نیست؛ به شرطی که
آدرس API تغییر نکرده باشد. HTTPS هر دو بخش را حفظ کنید تا کوکی ورود و تمدید نشست
با تنظیمات فعلی درست کار کند.

نصب‌کننده و راه‌انداز HTTPS فعلی برای 7000 و 4200 نوشته شده‌اند؛ ساخت بسته نصب تازه
با پورت سفارشی، هماهنگ کردن بررسی پورت‌ها، آدرس health و راهنمای نصب را هم لازم دارد.
توضیحات داخل XML سرویس صرفاً متن نمایشی هستند؛ محل تعیین پورت API در Kestrel
و پورت فرانت‌اند در server.listen است.

۱۱. مدیریت و عیب‌یابی سرویس‌ها
=============================
از فایل‌های همراه بسته استفاده کنید:
  2-Service-Status.cmd: وضعیت سرویس‌ها.
  3-Restart-Services.cmd: شروع یا راه‌اندازی مجدد، با دسترسی مدیر.
  4-Stop-Services.cmd: توقف دستی، با دسترسی مدیر.
  5-Uninstall-Services.cmd: توقف و حذف سرویس‌ها، با دسترسی مدیر.

باز شدن پنجره برای مدیریت طبیعی است؛ بعد از اتمام می‌توانید آن را ببندید.
برای مشاهده سرویس‌ها با رابط ویندوز، Win+R را بزنید و services.msc را اجرا کنید.
لاگ‌ها، با دسترسی مدیر:
  C:\ProgramData\AccountingStockService\services\logs

آدرس بررسی سلامت با پورت پیش‌فرض:
  https://localhost:7000/health

اگر SQL/VPN در دسترس نباشد، برنامه ممکن است در شروع خطا بدهد و سرویس بعداً دوباره
تلاش کند. اگر لازم شد پس از اتصال VPN سرویس‌ها را Restart کنید.
سرویس در وضعیت Running الزاماً به معنی سالم بودن اتصال SQL و ورود کاربران نیست؛
health، لاگ‌ها و یک عملیات واقعی برنامه را هم بررسی کنید.

حذف سرویس‌ها به‌صورت پیش‌فرض SQL، تنظیمات، گزارش‌ها یا پوشه نصب را حذف نمی‌کند.
برای نصب مجدد، از پوشه نصب بکاپ بگیرید و بعد از حذف سرویس‌ها نام پوشه حفظ‌شده
را عوض کنید؛ هنگام نصب تازه آن را به‌عنوان Old package folder معرفی کنید.

۱۲. Docker و تفاوت آن با بسته فعلی
=================================
Docker برنامه و وابستگی‌هایش را به شکل Image بسته‌بندی می‌کند؛ Container اجرای
آن Image است. Dockerfile دستور ساخت Image و Compose تعریف چند سرویس مرتبط است.
Volume داده را مستقل از عمر Container نگه می‌دارد، اما جای بکاپ دیتابیس را نمی‌گیرد.

فرمان‌های عمومی زیر برای پروژه‌ای هستند که Docker آن آماده و آزمایش شده باشد:
  docker compose up -d --build
  docker compose ps
  docker compose logs --tail 100 backend
  docker compose stop

-d اجرای پس‌زمینه است. down کانتینرها و شبکه‌های مربوط را جمع می‌کند؛ down -v
Volumeهای مدیریت‌شده مربوط را هم حذف می‌کند. برای دیتابیس کاری بدون بررسی و بکاپ
از down -v استفاده نکنید.

وضعیت همین پروژه:
  Dockerfile فعلی از تصویرهای Linux استفاده می‌کند، اما API فعلی net8.0-windows
  و Infrastructure وابسته به Microsoft.WindowsDesktop.App است. پس Dockerfile
  موجود برای اجرای همین نسخه روی Linux آماده نیست و قبل از استفاده باید سازگار شود.
  Compose موجود SQL جداگانه‌ای در کانتینر تعریف می‌کند و اتصال backend را به آن
  می‌فرستد؛ برای استفاده از SQL فعلی 192.168.100.92 باید اتصال و وابستگی‌ها تغییر کنند.
  HTTPS و رفتار کوکی‌ها نیز باید در استقرار Docker هماهنگ و بررسی شوند.

داخل Container، localhost به خود همان Container اشاره می‌کند. برای اتصال به SQL
جداگانه، نام یا آدرس قابل دسترسی آن را می‌دهید. Compose می‌تواند سرویس SQL داخلی
نداشته باشد و فقط برنامه را اجرا کند. در حالت SQL داخلی، داده SQL باید پایدار باشد؛
فایل‌های App_Data و گزارش‌های برنامه هم اگر داخل Container نوشته شوند، نیاز به
محل ذخیره پایدار و بکاپ دارند.

۱۳. روال پیشنهادی هر انتشار
==========================
  ۱) بررسی تغییرات و ثبت نسخه در Git.
  ۲) Build و Publish در پوشه خروجی تازه.
  ۳) بررسی خروجی، لاگ‌ها و رفتار برنامه با تنظیمات آزمایشی.
  ۴) بکاپ SQL و پوشه نصب مقصد.
  ۵) توقف سرویس‌ها و جایگزینی فایل‌های برنامه با حفظ تنظیمات و داده‌های مقصد.
  ۶) شروع سرویس‌ها و بررسی health، ورود، ثبت اطلاعات، گزارش‌گیری و چاپ.
  ۷) نگهداری نسخه قبلی و بکاپ متناظر برای بازگشت احتمالی.

رمز SQL، کلید JWT، کلید خصوصی گواهی، مجوز خصوصی گزارش‌ساز و ZIP حاوی آن‌ها را
در Git ثبت نکنید. گواهی نصب‌شده، اتصال SQL و کاربران واقعی به محیط مقصد تعلق دارند
و نباید برای هر نسخه جدید بی‌دلیل دوباره تولید یا بازنویسی شوند.

۱۴. تنظیم زمان ورود مجدد و خروج پس از بی‌کاری
===========================================
نسخه دارای SessionSettings، دو محدودیت مستقل دارد. در appsettings.json سورس
و در صورت نیاز appsettings.Production.json مقصد این بخش را قرار دهید:

  "SessionSettings": {
    "AbsoluteTimeoutSeconds": 86400,
    "IdleTimeoutSeconds": 3600
  }

واحد هر دو مقدار ثانیه است:
  86400 = بیست‌وچهار ساعت؛ سقف قطعی نشست از لحظه ورود.
  3600 = یک ساعت؛ خروج پس از بی‌کاری.
  برای مثال IdleTimeoutSeconds برابر 1800 یعنی نیم ساعت بی‌کاری.
مقادیر باید بین 1 و 31536000 باشند. بعد از ویرایش تنظیمات مقصد، سرویس‌ها را
Restart کنید. تغییر این دو مقدار نیازی به Publish مجدد ندارد، به شرطی که ابتدا
نسخه جدید دارای منطق نشست روی مقصد نصب شده باشد.

بخش جدید را کنار سایر بخش‌های JSON اضافه کنید؛ ConnectionStrings، JwtSettings
و Kestrel موجود را حذف یا بازنویسی نکنید. JwtSettings.Secret فعلی باید حفظ شود.
توکن دسترسی همچنان کوتاه‌عمر است، ولی Refresh اجازه عبور از سقف قطعی نشست را نمی‌دهد.
۲۴ ساعت در این تنظیم یعنی از لحظه ورود؛ نه تعویض روز تقویمی یا رأس نیمه‌شب.

فعالیت کاربر شامل حرکت اشاره‌گر، کلیک، تایپ، چرخاندن صفحه و لمس است. فعالیت
به‌صورت تجمیع‌شده، با فاصله حداقل حدود پنج ثانیه به سرور اعلام می‌شود. درخواست‌های
خودکار، بررسی لایسنس، باز بودن صفحه و تمدید توکن به‌تنهایی نشست را تمدید نمی‌کنند.
مبنای سمت سرور آخرین فعالیت تأییدشده است. سرور درخواست نشست منقضی‌شده را رد
می‌کند و مرورگر نیز به صفحه ورود هدایت می‌شود. اگر سیستم Sleep یا مرورگر متوقف
شود، کنترل مرورگر هنگام ادامه اجرا انجام می‌شود؛ API همچنان انقضا را مستقل بررسی می‌کند.

اطلاعات نشست در دیتابیس ذخیره می‌شود؛ Restart سرویس زمان شروع نشست را از نو
تنظیم نمی‌کند. مدل فعلی برنامه یک نشست فعال برای هر کاربر نگه می‌دارد؛ ورود تازه
با همان حساب، نشست قبلی را جایگزین می‌کند.

برای ارتقا به این نسخه، migration زیر سه ستون نشست را به Users اضافه می‌کند:
  20261020000000_UserSessionTimeouts
این migration در اولین شروع نسخه جدید، مطابق روال فعلی برنامه اعمال می‌شود.
پیش از ارتقا از SQL بکاپ بگیرید. نشست‌های قدیمی پس از ارتقا باید دوباره وارد شوند.
این تغییر، آدرس، حساب، رمز یا نام دیتابیس را عوض نمی‌کند.

بسته‌های ZIP ساخته‌شده پیش از این تغییر، منطق جدید را ندارند؛ برای اعمال روی
مقصد، خروجی جدید بک‌اند و فرانت‌اند را مطابق بخش‌های این راهنما جایگزین کنید.

سرویس‌های ویندوز در بسته نصب‌شده با روشن شدن سیستم خودکار بالا می‌آیند. خود
مرورگر خودکار باز نمی‌شود و SQL یا VPN باید قابل دسترسی باشد. پس از راه‌اندازی
ویندوز کافی است کاربر مرورگر و آدرس برنامه را باز کند.

۱۵. ساخت دیتابیس خام روی SQL جدید
================================
برای راه‌اندازی از صفر، از backend\database و راهنمای فارسی داخل همان پوشه استفاده کنید.
AccountingDb.Schema.sql ساختار همه migrationها از جمله نشست را دارد و فاقد رمز و
اطلاعات عملیاتی است. ابزار Accounting.DatabaseSetup داده‌های پایه فارسی، شعبه،
انبار، واحدها، نقش‌ها و حساب admin@demo.local را با رمز انتخابی شما می‌سازد.
برای تهیه ZIP مستقلِ آماده انتقال، در پوشه backend اجرا کنید:
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\database\Build-RawDatabase.ps1

در مقصد از Initialize-RawDatabase.cmd داخل ZIP استفاده کنید. فقط برای ساختار خامی
که قبلاً از طریق SQL ساخته شده، Initialize-ExistingRawSchema.cmd را اجرا کنید.
تنظیم اتصال SQL فعلی پروژه با این ابزار تغییر نمی‌کند؛ آدرس SQL مقصد را هنگام
اجرا انتخاب می‌کنید و اتصال برنامه نصب‌شده را جداگانه تنظیم می‌کنید.
برای شروع دیتابیس خالی در محیط Production، رمز اولیه باید صریحاً از ابزار یا
Seeding:AdminPassword تأمین شود؛ رمز پیش‌فرض عمومی برای مدیر Production وجود ندارد.
ابزار رمز موجود را بازنشانی و اطلاعات عملیاتی دیتابیس کاری را پاک نمی‌کند.
