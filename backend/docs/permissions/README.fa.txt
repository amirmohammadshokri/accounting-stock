گزارش بررسی دسترسی‌ها و SQL مجوزهای تخصیص‌نیافته
تاریخ: ۲۵ اکتبر ۲۰۲۶

۱) نتیجه بررسی سورس
فهرست اولیه بک‌اند و فرم نقش‌ها هر دو ۶۶ مجوز داشتند؛ هیچ نامی در فرم جا نیفتاده بود.
۱۱۵ اکشن API از نظر attributeهای سطح کنترلر و اکشن بررسی شدند؛ فهرست در
endpoint-permissions.csv است. احراز هویت، نشست و وضعیت عمومی اعتبار استثناهای عمدی‌اند.
این بررسی ایستا همه شرط‌های داخل بدنه اکشن یا همه سناریوهای کاری را شبیه‌سازی نمی‌کند.

موارد اصلاح‌شده:
- JWT تک‌مجوزی گاهی مقدار permission را string می‌فرستد. اکنون به آرایه تبدیل می‌شود؛
  داشتن Order.CreateInvoice به معنی داشتن Order.Create نیست.
- هنگام بازخوانی، مجوزهای ذخیره‌شده قدیمی از localStorage جای مجوزهای توکن نمی‌نشینند.
- منو و مسیر کاربران با User.Read و نقش‌ها با Role.Read کنترل می‌شوند؛ نام مدیر کافی نیست.
- دکمه ایجاد کاربر با User.Create، ویرایش و تغییر رمز با User.Update، حذف با User.Delete.
- فیلتر نقش/شعبه کاربران بدون Role.Read/Branch.Read درخواست غیرمجاز ارسال نمی‌کند.
- directive نمایش مجوز با تغییر currentUser واکنش نشان می‌دهد و دکمه قبلی را حذف می‌کند.
- شروع مجدد برنامه دیگر مجوز حذف‌شده نقش ثابت مدیر را خودکار برنمی‌گرداند.
  مدیر جدید در نصب تازه همچنان با همه مجوزهای فعلی ساخته می‌شود؛ نقش موجود حفظ می‌شود.
- مسیر پیش‌فرض برای دارنده صرفاً Order.Create یا Invoice.Create به صفحه ایجاد می‌رسد.
  کاربر بدون مجوز صفحه تجاری به تنظیمات ظاهر می‌رود و در حلقه login/dashboard نمی‌افتد.
- داشبورد بدون Branch.Read با شعبه کاربر کار می‌کند و فهرست شعبه‌های غیرمجاز را نمی‌گیرد.
- موجودی و گردش انبار بدون Warehouse.Read درخواست فهرست انبارها نمی‌فرستند.

۲) مجوزهای جاافتاده‌ای که اضافه شدند
Audit.Read: اکشن مشاهده سوابق فعالیت قبلاً فقط ورود کاربر را لازم داشت؛ اکنون مجوز مستقل دارد.
DataMaintenance.Read: مشاهده آمار مدیریت داده‌ها، علاوه بر نقش مدیر.
DataMaintenance.Reset: پاک‌سازی اطلاعات، علاوه بر نقش مدیر، رمز و تاییدهای قبلی.
فرم پاک‌سازی بدون Reset پنهان است و متد آن هم مجوز را بررسی می‌کند.
اکنون کاتالوگ بک‌اند و فرم نقش‌ها هر دو ۶۹ مجوز دارند.
برای نقش‌های موجود، این سه مجوز خودکار اضافه نمی‌شوند؛ فقط به نقش موردنظر تخصیص دهید.
برای مدیریت داده‌ها نقش مدیر سامانه/Admin همچنان شرط اضافی است؛ مجوز تنها کافی نیست.
برای استفاده معمول صفحه پاک‌سازی، Read و Reset هر دو لازم‌اند.
مجوز Audit.Read در فرم نقش‌ها دیده می‌شود؛ صفحه منوی مستقل سوابق در این تغییر ایجاد نشده است.

Cheque.Update در کاتالوگ هست ولی اکشن ویرایش عمومی چک وجود ندارد؛ تخصیص آن به تنهایی
کاری را فعال نمی‌کند. برای تغییر وضعیت باید Cheque.UpdateStatus داده شود.
Invoice.Delete هم در API تعریف و استفاده شده است؛ این کار قابلیت جدید حذف در UI ایجاد نمی‌کند.

۳) چگونه دقیقاً فقط مجوز انتخابی دیده شود؟
مجوز موثر کاربر اجتماع تمام نقش‌های فعال اوست. اگر نقش دوم یا نقش مدیر پرمجوز دارد،
برداشتن یک گزینه از نقش اول، مجوز نقش دوم را حذف نمی‌کند. ابتدا نقش‌های کاربر را بررسی کنید.
برای کاربر محدود، نقش اختصاصی بسازید و فقط مجوزهای موردنظر را تیک بزنید.
مثال: فقط Invoice.Read => منوی فاکتورها، بدون ایجاد/ویرایش و سایر ماژول‌های تجاری.
تنظیمات ظاهر و خروج برای کاربران واردشده مشترک‌اند و مجوز تجاری محسوب نمی‌شوند.
مجوز Create بدون Read معمولاً فهرست آن ماژول را باز نمی‌کند. فرم‌های ثبت ممکن است برای
انتخاب کالا، طرف حساب، انبار یا شعبه به مجوز خواندن همان مرجع نیاز داشته باشند؛
این وابستگی‌ها نباید با اعطای خودکار همه دسترسی‌ها حل شوند.
بعد از تغییر نقش یا مجوز، کاربر خروج و ورود کند؛ JWT قبلی تا تمدید/انقضا تصویر قبلی
مجوزها را دارد. این تغییر مکانیزم ابطال فوری همه توکن‌ها هنگام ویرایش نقش اضافه نمی‌کند.

۴) اجرای SQL برای تشخیص موارد تخصیص‌نیافته
فایل: audit-and-add-missing.sql
این اسکریپت به SQL واقعی شما در این کار متصل یا روی آن اجرا نشده است؛ نتیجه تخصیص‌های
دیتابیس مقصد را فقط پس از اجرای گزارش روی همان دیتابیس می‌توان قطعی دانست.
فهرست مجوزها در این فایل از ۶۹ ثابت فعلی سورس ساخته شده است.

الف) در SSMS دیتابیس مخصوص برنامه را انتخاب کنید و اسکریپت را باز کنید.
ب) بار اول @RoleId=NULL و @Apply=0 بمانند؛ اجرا، فهرست نقش‌ها، نقش‌های هر کاربر،
   مجوزهای موثر و نام‌های ناشناخته را نمایش می‌دهد؛ هیچ رکوردی تغییر نمی‌کند.
ج) ID نقش موردنظر را در @RoleId قرار دهید و @Apply=0 نگه دارید؛ دوباره اجرا کنید.
د) جدول MissingPermission/SuggestedSql همه مجوزهای تخصیص‌نیافته آن نقش را با
   SQL جداگانه هر مورد نشان می‌دهد. تخصیص‌نیافته بودن الزاماً نقص نیست؛
   بیشتر نقش‌ها عمداً نباید همه مجوزها را داشته باشند.
هـ) فقط مواردی را که می‌خواهید اضافه کنید در @Requested وارد کنید؛ مثلاً:

DECLARE @Requested table (Permission nvarchar(150) PRIMARY KEY);
INSERT @Requested VALUES (N'Audit.Read');

این INSERT را زیر DECLARE موجود در فایل اضافه کنید؛ DECLARE را دوباره تکرار نکنید.
برای مدیر مسئول پاک‌سازی، در صورت نیاز واقعی:
INSERT @Requested VALUES (N'DataMaintenance.Read'), (N'DataMaintenance.Reset');

و) ابتدا با @Apply=0 نتیجه Will add را ببینید. سپس اگر درست است @Apply=1 کنید.
اسکریپت فقط @Requested را اضافه می‌کند؛ مجوزها یا نقش‌های قبلی را حذف نمی‌کند و اجرای
مجدد آن رکورد تکراری نمی‌سازد. به حسابی با حق درج در RolePermissions نیاز دارد.
بعد از تغییر مجوزها خروج و ورود مجدد انجام شود. برای اعمال کدها، API و فرانت‌اند
هر دو دوباره Build و Publish شوند؛ migration ساختار جدید لازم نیست.
ستون‌های فعلی RolePermissions یعنی RoleId، Permission، CreatedAtUtc و UpdatedAtUtc استفاده شده‌اند.
در این پروژه جدول مستقل Permissions وجود ندارد؛ ساخت چنین جدولی لازم نیست.

۵) بررسی و انتشار
۳۴ تست فرانت‌اند و ۱۴ تست هدفمند بک‌اند پاس شدند (۱۱ تست راه‌اندازی/مجوزها و ۳ تست HTTP مستقل).
برای بررسی قالب‌های تمام صفحات از ngc --noEmit -p tsconfig.app.json استفاده شد.
راه انتشار مطابق docs/IIS-PRODUCTION-COMPLETE.fa.txt است.
